# 资金混淆（金额/手数 ×k 假值）— 路线对比文档

> 状态：方向已定（见下），**路线 A vs B 待拍板**。本文件先做对比，拍板后改写为正式实施方案。

## Context（为什么做）

希望：好友/群看复盘分享、看板时，**看不到真实账户体量和真实盈亏**。
核心诉求有二，按重要性：
1. **管理员也查不到真金额**（自托管，管理员=项目拥有者，能读数据库）。
2. 好友/群看到的金额是假的，但复盘仍然有效。

## 已锁定的方向（不再讨论）

- **混淆手段**：真实金额与手数**同乘一个系数 k**，变成假值上传/显示。
  - 乘 k 的量纲：**货币金额**（profit/balance/equity/commission/swap/fee/sl_profit/tp_profit）+ **手数** volume。
  - **绝不乘 k 的量纲**：价格（open/close/price/sl/tp、K 线 OHLC）。价格是公共数据轨道（bars 按券商 source 全局共享），且复盘要真实价位。
  - 自洽性证明：盈亏 =（平仓价−开仓价）× 手数 × 乘数。价格真实、手数×k → 算出的盈亏自然×k，与显示的假盈亏对得上，好友怎么验证都自洽，看不出破绽。账户体量(净值/余额)×k 隐藏真实规模。盈亏比=价格差决定，真实，复盘价值保留。
- **k / seed**：本机随机 seed 派生 k，seed **不上传**；给**恢复码**（seed 编码）供换设备还原。
- **本人看真值**：本机有 seed → 显示层 ÷k 还原真值；好友/群/管理员看假值。
- **三层兜底**：本机 seed → 恢复码 → 重新生成新 seed（历史假值作废，从 EA/MT5 重拉原始数据按新 k 重算）。
- **还原范围**：所有页面（/chart React + /board /history 静态页）都还原。
- **开关**：账户级开关，可切换，切换/换 k 时提示“账户曲线会重算”。
- **存量**：不清洗历史真值；UI 提示“开启前的旧分享仍是真金额”。
- **k 取值**：让假手数落在合理区间（约 0.01–50 手）、假净值落在合理量级，避免假值荒唐暴露混淆。

## 调研确认的关键事实（决定路线）

**SyncNote 是多路上传，金额从三条独立路径进库：**

| 路径 | 触发者 | 经过浏览器? | 带真金额的入口 |
|---|---|---|---|
| **浏览器代传** | SyncTrade + 网页开着 | ✅ 是 | `/api/mt5/history-import`（raw deals）→ 服务器 `sync_history.summarize` 重算 profit |
| **EA 直传** | SyncNote EA（关网页也传） | ❌ 否 | `/api/mt5/history-sync`（`bridge/SyncNote.mq5:309`，raw deals） |
| **bridge_push** | 独立 Python 进程 | ❌ 否 | `/api/snapshot`（balance/equity/positions，`tools/bridge_push.py:155`） |

**致命细节**：
- profit 不是客户端上传的，是服务器用 **raw deals** 重算的（`sync_history.py:92-130 summarize`）。
- **raw deals 原样存进 `mt5_raw_deals` 表**（`sync_history.py:169`）——就算重算结果变假值，原始真金额仍在库里，管理员查 `mt5_raw_deals` 就看到真值。
- 所以要让管理员查不到，**客户端必须在上传前把每条 raw deal 的 profit/commission/swap/fee/volume 乘好 k 再传**（价格 price 不乘），让 `mt5_raw_deals` 和 `trades` 都只存假值。
- 但 EA 直传 和 bridge_push **不经过浏览器，拿不到 k**——这两路上传的就是真值。

**→ “客户端乘 k”只能管住浏览器代传那一路。这是整个方案的核心约束。**

---

## 路线 A：只管浏览器代传

**做法**：只在 `localHistorySync.ts` 上传前拦截 `page.deals`，逐条把货币金额+volume 乘 k（price 不乘）再传。EA 直传 / bridge_push 不动。

**改动面**：
- 前端：`localHistorySync.ts:217` 构造 body 前对 deals 乘 k；新建 seed/k 模块（挂 `prefs.ts` 风格，复用 `localHistorySync.ts:81` 的 `crypto.subtle.digest` 派生）。
- 显示层还原：`api.ts` 的 `money()`（15 处调用）接 ÷k；静态页 `app.js`/`history.js`/`journal-ui.js` 各自的 `money` 也接。
- 账户开关全链路：`app_server.py` L89/L147/L959/L963 + `profile.html`/`profile.js`（照 auto_history_sync 模板）。

**安全边界（缺陷）**：
- ❌ 用户一旦挂 SyncNote EA 直传，或跑 bridge_push，**真值照样进 `mt5_raw_deals`/`trades`/`snapshots`**，管理员可见，混淆形同虚设。
- 必须强制“开了混淆 = 禁用 SyncNote EA 直传 + 禁用 bridge_push，只能用浏览器代传”，否则是安全假象。但这又和“关浏览器也能后台归档”的价值冲突。
- 实时快照（bridge_push 的 balance/equity）走 `/api/snapshot`，网页端 board 也可能用 live 内存值——需确认本机连接时 board 的 equity 来源是否也绕过了 k。

**工作量**：中。不碰 EA、不碰 MQL5。

---

## 路线 B：所有上传源都乘 k

**做法**：浏览器、SyncNote EA（MQL5）、bridge_push（Python）三端都在上传前乘 k。

**改动面**：
- 路线 A 的全部，**外加**：
  - `bridge/SyncNote.mq5`：上传成交前对每条 deal 的 profit/commission/swap/volume 乘 k；要在 EA 里实现 seed→k 派生，或让用户在 EA input 填恢复码/k。碰刚调好的 EA。
  - `bridge/SyncTrade.mq5`：同上（它也能直传/被代传）。
  - `tools/bridge_push.py`：balance/equity/positions/history 乘 k，同样要拿到 k。
  - **k 三端一致问题**：浏览器的 k 来自本机 seed，EA/bridge_push 怎么拿到同一个 k？只能让用户在 EA 参数、bridge_push 配置里**手填恢复码**，三端各自派生出同一个 k。用户配置负担重。

**安全边界**：
- ✅ 三路上传全乘 k → `mt5_raw_deals`/`trades`/`snapshots` 全是假值，管理员查不到真值。诉求达成。
- 但 k 要出现在 EA input / bridge_push 配置里（明文填恢复码），这些配置文件若被读，k 泄漏 → 可还原。本机文件安全性问题。

**工作量**：大。碰两个 EA（MQL5，需重新编译）、bridge_push、且引入“三端 k 一致”的配置复杂度。违背 EA“只读数据源”的单一职责。

---

## 第三种可能（供讨论）：收窄诉求，放弃“管理员查不到”

如果能接受**“对好友/群隐藏，但管理员（=自己）能查到真值”**，则：
- 服务器照常存真值（三路上传都不用改）。
- 只在**对外出口**（board 给好友的快照、/api/chart/entry 给好友/分享的 trade、inbox）按“查看者是不是本人”决定：本人返回真值，好友返回 ×k 假值。k 存服务器（管理员可见，但管理员=自己，不介意）。
- 本人任意设备看真值（服务器发真值），好友看假值。无需 seed/恢复码/客户端改造。
- **工作量最小**，只改 server 出库 + 开关。
- 代价：管理员能查到真值——但“管理员”就是用户自己（自托管单管理员），这个诉求是否真的必要？值得重新确认。
