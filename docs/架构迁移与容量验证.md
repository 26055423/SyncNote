# 架构迁移与容量验证

更新：2026-11-10。本次保持 Python 标准库、SQLite WAL 和 React/Vela 技术栈，建立显式生命周期与模块边界。

## 数据库版本与兼容性

正常运行 `python3 app_server.py` 会先升级，再接受请求。`python3 app_server.py --migrate` 只升级后退出。导入模块不建库、不改数据、不启动线程。

| 版本 | 迁移结果 |
|---|---|
| 3 | 接管旧 version=2，补齐基线并建立 schema_migrations |
| 4 | source=syncnote-history.v1 留在 trades；其他摘要迁入 legacy_trades；trade_keys 成为笔记/复盘的稳定外键 |
| 5 | review_snapshots 存不可更新内容，review_shares 存投递/已读；群卡片指向独立快照 |

全部待执行步骤在一个升级事务中完成。失败回滚结构、数据和版本记录；迁移末尾验证外键。相同版本重复执行不再改写内容；高版本数据库不能被低版本代码打开。

旧分享 id 保持不变，旧表归档为 legacy_review_shares。原先没有冻结的内容按升级时状态冻结；已经被旧版 upsert 覆盖的内容无法找回。无法可靠判定来源的旧投递保持原有私信可见性；新群投递不混入私信。快照包括笔记、画线、锚点和留言，成交与 K 线仍从当前数据源读取。

旧摘要仍可通过原交易链接查看。主历史在存在权威记录时只显示权威记录，避免重复计数；此前只有摘要的账户继续显示旧数据和来源提示。迁移不把摘要伪造成原始 deal。

## 升级与回滚

升级后的数据库不能直接配旧代码运行。回滚必须恢复同一备份时刻的代码与数据库，停服期间完成，不能把正常上线后产生的新记录丢进自动回滚。

systemd 部署须在升级前安装本次版本的 `tools/syncnote-pull.sh`（由管理员把审核后的文件复制到服务器，再执行安装）：

```sh
sudo install -m 755 -o root -g root /tmp/syncnote-pull.sh /usr/local/bin/syncnote-pull
sudo syncnote-pull
```

新版更新器检查干净工作树和快进关系，fetch 后从目标提交取备份工具到临时文件；停服务，使用 SQLite backup API 保存包含 WAL 已提交内容的快照，再快进代码并启动。30 次健康检查仍失败时，同时恢复旧代码和数据库。备份保留在 `/var/backups/syncnote/`，目录 700、文件 600；不进入仓库。

第一次安装版本化迁移时，不能先用旧更新器拉取再指望新代码自动接管旧脚本的回滚行为。Docker 部署同样先备份命名卷，失败时恢复匹配的数据库与镜像。目录交换式部署保留原目录数据副本，迁移只作用于新目录。

手工快照与恢复工具：

```sh
python3 tools/database_backup.py /path/board.sqlite3 /path/backup.sqlite3
# 恢复前必须停止所有使用目标库的进程。
python3 tools/database_backup.py /path/backup.sqlite3 /path/board.sqlite3 --restore
```

备份拒绝覆盖现有文件；恢复原子替换目标并清理旧 WAL/SHM，保留目标权限。恢复后再次启动服务检查健康。当前只完成本地代码和合成数据验证，没有执行本次线上迁移。

## 可观测性与容量基线

`GET /api/admin/metrics` 使用统一 require_admin：普通用户 404；管理员仍需 15 分钟 sudo。固定指标类别为 HTTP GET/POST、db.execute、catalog.refresh。记录总数、错误数、≥250ms 次数、最大值及最近 512 次的 p50/p95；不保存 SQL、参数、请求 URL 或身份。db.execute 只测执行阶段，完整读取/序列化耗时应看 HTTP 或容量工具。重启后清零。

容量工具只生成临时数据，不读取 DATA_DIR，退出自动清理：

```sh
python3 tools/capacity_probe.py --users 100 --trades 500 --bars 100000 --workers 8 --requests 160
```

2026-11-10 本机 Darwin arm64 / Python 3.13.12，100 个合成用户、各 500 笔成交、10 万根 K 线、8 个工作线程、160 次混合操作：

| 操作 | p50 | p95 |
|---|---:|---:|
| 单用户完整历史读取 | 43.47 ms | 52.36 ms |
| 2000 根 K 线及覆盖读取 | 296.17 ms | 341.01 ms |
| 分享收件箱读取 | 25.81 ms | 32.49 ms |
| 活跃状态写入 | 1.67 ms | 11.69 ms |

总耗时 1.77s，约 90.22 次操作/s，错误 0；目录刷新 103.33ms，数据库约 28.5MiB。它是本机数据库/领域函数混合负载，**不是 100 人同时在线的 HTTP 容量证明**，也未覆盖百万级 K 线、完整好友看板、长时间锁等待或真实 EA 并发上传。

当前优先保留单体部署，按测量决定下一步：看板历史分页/增量返回、K 线范围查询优化、缓存大小边界、长写事务拆分。没有证据要求现在引入消息队列或微服务。
